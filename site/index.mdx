## Agent security is just CI security

A coding agent working on an issue is the same kind of risk as a build
script from a pull request or a dependency's install hook: code you did
not write, steered by text you did not write, on a machine that holds
your tokens. agentic-job gives all three the same defence.

## Try it in a workflow

Any job can harden its runner with one step, as in the
[README](../README.md#core-features); pin `COMMIT` to a commit you have
read. Everything that needs root goes before it.

```yaml
jobs:
  build:
    runs-on: ubuntu-26.04
    steps:
      - run: sudo apt-get install -y libfoo-dev   # root: before the step
      - uses: actions/checkout@v7
      - uses: cgwalters-forge/actions/secure-host@COMMIT
      - run: make check                           # runner's user, no sudo
```

To run an agent, [example.yml](../.github/workflows/example.yml) is a
whole caller of the reusable workflow to copy, with the scripted agent,
which needs no model.

## Compared with GitHub Agentic Workflows

For most people [gh-aw](https://github.github.com/gh-aw/) is the right
choice today: it has far more output types and triggers, and memory
across runs. agentic-job checks and applies gh-aw's safe
outputs with gh-aw's own pinned code, but runs the agent as an
unprivileged user on a hardened runner rather than in a container, so
the work can use containers, `/dev/kvm` and user namespaces, and you
write ordinary workflow YAML with no compiler.
[The comparison](../docs/background-ghaw.md) lists the differences item by item.
