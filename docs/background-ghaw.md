# Comparison with GitHub Agentic Workflows

> This text was generated by an LLM (cgwalters-bot). cgwalters has not reviewed it yet.

[gh-aw](https://github.com/github/gh-aw) is the source of the safe-outputs
format and the collector and handlers used here. The
[README](../README.md#why-not-github-agentic-workflows) explains why this
project uses a host-user sandbox instead of gh-aw's container runtime.
This page compares features, not deployment instructions.

The gh-aw descriptions below come from its source and documentation at
v0.91.4 (October 2026). They are not a review of later releases.

## Workflow and execution

gh-aw compiles Markdown with YAML frontmatter into a locked Actions
workflow. Its compiler selects engines, permissions, firewall settings,
activation, detection and output jobs. agentic-job accepts ordinary YAML
that calls a reusable workflow pinned by commit. It has no compiler or
caller-side strict-mode lint; [compiler.md](compiler.md) explains that choice.

gh-aw's default runtime puts the agent behind a domain-allowlist firewall
in a container. agentic-job uses a second Unix user on a disposable host
with uid-keyed network rules and mitmproxy. Reads are open except for a
threat feed; writes require a rule. This supports rootless podman and
host KVM access but shares the host kernel. An egress allowlist is still
[#116](https://github.com/cgwalters-forge/agentic-job/issues/116).
gh-aw also offers a preview cloud-hypervisor runtime; it has not been
evaluated here.

gh-aw's API proxy holds the model key on the runner. agentic-job gets a
per-run token from a broker on another machine. Claude Code and opencode
are configured by code and driven over ACP. Adding an engine requires
code, not a caller-supplied command. Interactive attachment is planned,
not an available advantage today.

## Triggers and task context

agentic-job's `event: true` path implements event admission, exact role
and bot bounds, fork restrictions, slash commands, reactions and status
comments. Its label example filters a label in the caller's YAML; it does
not consume the label as gh-aw's `label-command` does
([#117](https://github.com/cgwalters-forge/agentic-job/issues/117)).
[events.md](events.md) owns the admission and task-context details.

Event text is stripped of control and format characters, capped and
fenced. It is not gh-aw's full sanitizer: URL filtering, normalization
and homoglyph mapping are absent. The caller supplies one standing task;
there is no Markdown templating or import language.

Deadline guards are implemented. Cooldown and rolling user quotas are
CLI groundwork requiring complete trusted admitted-start history; the
reusable workflow does not supply it. Search guards, check-status guards,
daily spend guards and organization bounds wiring remain
[#118](https://github.com/cgwalters-forge/agentic-job/issues/118).
Caller concurrency is not an atomic quota or a FIFO queue.

## Tools and outputs

gh-aw has a read-only GitHub MCP gateway with its own credential and
per-tool limits. agentic-job has no authenticated read gateway; the agent
can use the public API unauthenticated through the proxy.
That integration is [#112](https://github.com/cgwalters-forge/agentic-job/issues/112).
Other MCP integrations and browser tooling are
[#120](https://github.com/cgwalters-forge/agentic-job/issues/120).

gh-aw validates safe-output tool calls as the agent makes them.
agentic-job asks the agent to write JSONL and validates it after the run.
Both use the same pinned collector and handlers. agentic-job currently
supports `create_pull_request`, `create_issue`, `add_comment`, `noop`,
`missing_tool` and `missing_data`, not gh-aw's whole catalogue.
Issue labels have allowed and blocked bounds; other target-specific
rules remain [#113](https://github.com/cgwalters-forge/agentic-job/issues/113).

agentic-job adds total output, patch byte and file caps, strict patch
parsing, and apply-time base and changed-path checks. It refuses a
pull-request fallback that would open an unrequested issue. Partial
runs require explicit opt-in and are marked before apply.
[safe-outputs.md](safe-outputs.md) describes the boundary.

gh-aw can run model-based threat detection before apply. There is no
equivalent here ([#114](https://github.com/cgwalters-forge/agentic-job/issues/114)).
Memory, staged mode and maintenance are also absent
([#119](https://github.com/cgwalters-forge/agentic-job/issues/119),
[#121](https://github.com/cgwalters-forge/agentic-job/issues/121)).

## Operations

The offline `agentic-job audit` command reads artifacts and reports tool
errors, denials, output refusals and estimated cost. Missing evidence is
not success. It does not replay code or send telemetry. OTLP export is
deferred ([#122](https://github.com/cgwalters-forge/agentic-job/issues/122)).

Private targets are refused here
([#115](https://github.com/cgwalters-forge/agentic-job/issues/115)); gh-aw
supports them. Apply uses a job token or an environment secret, without
gh-aw's computed permission union or per-run App-token integration.

## Related gh-aw deployments

earlier host-user-runtime fork. It is not the code agentic-job runs.
