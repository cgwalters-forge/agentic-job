# The sandbox: a hardened host, not a container

> This text was generated by an LLM (cgwalters-bot). cgwalters has not reviewed it yet.

What `agentic-job sandbox setup` does to a machine, and why. The code is
`crates/agentic-job/src/sandbox/` and `egress/`
([layout](layout.md)); the probes that prove it are in
[sandbox-check.md](sandbox-check.md), the requirements it serves in
[requirements.md](requirements.md), and how a workflow calls it in
[workflow.md](workflow.md).

## What it assumes

The agent is treated as a hostile process. It reads text that anyone can
write (issues, pull requests, CI logs, a repository's own files), so the
design assumes prompt injection succeeds. What then matters is what the
process can reach: no credential of the job's, no way out of its user,
and no network path that carries data out in a write.

The boundary is a second Unix user on the same machine. It is not a
kernel boundary: a local privilege escalation in the kernel, systemd or
sudo defeats it. So the machine must be a VM used for one job, and
`sandbox setup` refuses one it has set up before (`/etc/agentic-job`
exists), a sandbox user that is already there unless
`sandbox.allow-existing-user` says the image ships it, and a home left
without its user. Every refusal comes before the first change.

## Why not a container

gh-aw runs the agent in a container behind a firewall, with the
container runtime's socket hidden. The work this was built for is on
bootable containers: it builds images with rootless podman and boots
VMs through `/dev/kvm`. Those need the host, or a container weakened
until it is no longer the boundary
([background](https://github.com/cgwalters-forge/gh-aw/issues/1)). So
the host is hardened and the agent gets an ordinary login session on it.

What the code does for those two is small. For podman, setup requires
that the sandbox user has subordinate uids and names them in the network
rules, and `run0` gives each command the session rootless podman relies
on; podman itself is a package the caller lists. For KVM, the sandbox
user's groups default to `kvm`, and setup refuses when a listed group
does not exist. Nothing checks that `/dev/kvm` is there, and nothing in
this repository boots a VM as the sandbox user.

## What `sandbox setup` does

It runs as root, once, from a configuration with three tables that
concern it: `[sandbox]` (and `[sandbox.check]`), `[egress]` (`proxy`,
`direct`, `policy`) and `[setup]` (`packages`, `npm`, `script`). In
order, it:

- creates the user (`runner-sandbox` unless named), with a home, a group
  of its own and `sandbox.groups`; groups that are root by another name
  (`docker`, `wheel`, `adm`, `libvirt` and the like) are refused;
- drops `XDG_RUNTIME_DIR` and any `ACTIONS_*` variable from
  `/etc/environment`;
- sets mode 0700 on the runner user's home, `/opt/hca`,
  `/var/run/tailscale` and `sandbox.private-dirs`;
- stops the units of `sandbox.stop-services`;
- installs `setup.packages` (dnf or apt) and `setup.npm`, as root and on
  the open network; npm versions must be exact;
- denies the sandbox user sudo, every polkit action, cron, at and
  lingering;
- starts the egress proxy and loads the network rules (below);
- removes world-write from files and directories on the root filesystem
  outside `/tmp` and `/var/tmp`, and raises `ptrace_scope` from 0 to 1;
- runs `setup.script` as the sandbox user, never as root;
- installs the root-owned helper and configuration under `/etc/agentic-job/`;
- by default, locks the runner's user out of general sudo and polkit,
  closes root-equivalent group access and strips unowned setuid-root
  programs. [The lock and its probes](sandbox-check.md#after-setup-nothing-has-root)
  describe the remaining privileged operations.

Every command in the sandbox is then started through the root-owned
helper, which invokes `run0 --pipe --user=…`. This creates a transient
service with its own PAM session
and none of the caller's environment. It gets a fixed `PATH` and `LANG`,
the proxy's variables and `sandbox.env`; a variable named `ACTIONS_*`
(the job's identity-token request is two of them) is refused by name in
the configuration and again at entry. `--pipe` needs systemd 257; setup
checks only that `run0` is there.

## Network

The nftables rules match the sandbox user's uid and its subordinate
uids, so containers are covered, and reject rather than drop. The cloud
metadata address is always rejected. With `egress.proxy` (the default),
everything else is rejected too except loopback, and loopback's port 53
with it: the proxy resolves names. `egress.direct` lists endpoints
reached without the proxy, each an IPv4 address and port on the tailnet;
it is for the [inference proxy](inference.md), so that the run token
never crosses the egress proxy. With any, the rest of the tailnet is
rejected by name as well. The proxy's own uid is rejected on the tailnet
and on private, loopback and link-local addresses, except for port 53,
which it may open on any address off the tailnet
([#21](https://github.com/cgwalters-forge/agentic-job/issues/21)). The loaded text stays
in `/etc/agentic-job/rules.nft`.

The design follows a suggestion cgwalters made for the gh-aw fork
([comment](https://github.com/cgwalters-forge/gh-aw/issues/1#issuecomment-5958830932)).

## The egress proxy stays mitmproxy

The proxy is the one piece that is not Rust. The policy needs the
method and path of every request, so the proxy has to end TLS, and a
proxy that ends TLS is security-critical code that should not be
written again here. Asked about a new one in Rust, cgwalters said:
"That doesn't sound like a good idea". One that did not end TLS could
only allow by host name, and would lose the rule that reads are open
and writes are not.

So [mitmproxy](https://mitmproxy.org), pinned in
`egress/requirements.txt`, runs the addon and policy of `egress/`,
which the binary carries. Setup installs it into a Python environment
and starts it on `127.0.0.1:3128` as the user `egress-proxy`, in a
transient unit with no capabilities and a read-only system. The key of
its certificate authority stays in that user's state directory; the
certificate is published in `/etc/egress-proxy`, and the sandbox user's
environment points `HTTPS_PROXY` and the bundle variables of `git`,
`cargo`, `curl`, Node and Python at both.

A `GET`, `HEAD` or `OPTIONS` without a body may go to any host that is
not on a threat feed. Anything else, a WebSocket and a read with a body
included, needs a `[[write]]` rule: the ones shipped allow `git fetch`
from six forges and `npm audit`, and `egress.policy` replaces them. A
push is refused. So is a request whose `Host` header or TLS name is not
the host it connected to, and with raw TCP off, anything in a tunnel
that is not HTTP. A refusal is a 403 with the reason in
`X-Egress-Denied`. The log is one JSON line per request with method,
host, path and decision, never headers, bodies or query strings; `run`
copies the part written during the run into the transcript.

## What is tested

`sandbox check` probes all of this as the sandbox user, each probe with
a positive control. `run` does not repeat it: before the agent starts
it runs only its own probes that the run token is nowhere but the
agent's configuration. CI's `sandbox` job runs setup and the check for
real on hosted `ubuntu-26.04`, then removes each
protection in turn and requires that the matching probes fail
(`tests/sandbox_host.rs`), after showing that setup refuses a machine
that is not fresh (`tests/sandbox_fresh.rs`). What that runner cannot
show, and what was tried by hand elsewhere, is
[listed with the probes](sandbox-check.md#where-each-probe-has-been-seen-to-fail).

## What it does not do

- The runner's user still owns the checkout, caches and job credentials,
  and has unrestricted network access. Removing its root does not make
  it safe to run untrusted code as that user. `sandbox.lock-runner = false`
  also keeps its general sudo access.
- Reads are open, so data can leave in a `GET` to a host that is not on
  the feed. The feed is fetched once, at setup; a fetch that fails, or
  returns fewer than 1000 entries, leaves the proxy without one, with a
  warning.
- With `egress.proxy = false` the sandbox user's network is open but for
  the metadata address, and the tailnet when `direct` has entries.
- A container the agent starts has no network of its own. It reaches the
  proxy only on the host's network, and trusts it only if the
  certificate is mounted into it, as the probes do; nothing configures
  podman to do either.
- The agent can read whatever is world-readable on the host, and connect
  to whatever listens for every local user unless the caller stops it.
- `setup.npm` runs the packages' install scripts as root, which is why
  the list is the caller's and never the task's.
- Setup needs Python's `venv`, a package index, `curl` and `nft` on the
  machine. It has run on `ubuntu-26.04` in CI; other images are the
  caller's to try.
