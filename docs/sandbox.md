# The sandbox: a hardened host, not a container

> This text was generated by an LLM (cgwalters-bot). cgwalters has not reviewed it yet.

What `agentic-job sandbox setup` does to a machine, and why. The code is
`crates/agentic-job/src/sandbox/` and `egress/`
([layout](layout.md)); the probes that prove it are in
[sandbox-check.md](sandbox-check.md), the requirements it serves in
[requirements.md](requirements.md), and how a workflow calls it in
[workflow.md](workflow.md).

## What it assumes

The agent is treated as a hostile process. It reads text that anyone can
write (issues, pull requests, CI logs, a repository's own files), so the
design assumes prompt injection succeeds. What then matters is what the
process can reach: no credential of the job's, no way out of its user,
and no network path that carries data out in a write.

This protects against the sandboxed process, not an untrusted workflow running
outside the sandbox. A merge queue executes proposed workflow files and code
with write and OIDC permissions before landing. The
[ingress checker](workflow-ingress.md#merge-queue) vets each merge group, but
the group's own workflow definition runs it; human approval before enqueueing is the trust gate, including for
workflow steps that build or execute the proposed binary outside the sandbox.

The boundary is a second Unix user on the same machine. It is not a
kernel boundary: a local privilege escalation in the kernel, systemd or
sudo defeats it. So the machine must be a VM used for one job, and
`sandbox setup` refuses one it has set up before (`/etc/agentic-job`
exists), a sandbox user that is already there unless
`sandbox.allow-existing-user` says the image ships it, and a home left
without its user. Every refusal comes before the first change.

## Why not a container

gh-aw runs the agent in a container behind a firewall, with the
container runtime's socket hidden. The work this was built for is on
bootable containers: it builds images with rootless podman and boots
VMs through `/dev/kvm`. Those need the host, or a container weakened
until it is no longer the boundary
([background](https://github.com/cgwalters-forge/gh-aw/issues/1)). So
the host is hardened and the agent gets an ordinary login session on it.

What the code does for those two is small. For podman, setup requires
that the sandbox user has subordinate uids and names them in the network
rules, and `run0` gives each command the session rootless podman relies
on; podman itself is a package the caller lists. For KVM, the sandbox
user's groups default to `kvm`, and setup refuses when a listed group
does not exist. Nothing checks that `/dev/kvm` is there, and nothing in
this repository boots a VM as the sandbox user.

## What `sandbox setup` does

It runs as root, once, from a configuration with three tables that
concern it: `[sandbox]` (and `[sandbox.check]`), `[egress]` (`proxy`,
`direct`, `policy`) and `[setup]` (`packages`, `npm`, `agents`, `script`). In
order, it:

- creates the user (`runner-sandbox` unless named), with a home, a group
  of its own and `sandbox.groups`; groups that are root by another name
  (`docker`, `wheel`, `adm`, `libvirt` and the like) are refused;
- drops `XDG_RUNTIME_DIR` and any `ACTIONS_*` variable from
  `/etc/environment`;
- sets mode 0700 on the runner user's home, `/opt/hca`,
  `/var/run/tailscale` and `sandbox.private-dirs`;
- stops the units of `sandbox.stop-services`, with the sockets, paths
  and timers that trigger them, and masks them all until reboot, so that
  nothing starts one again after `sandbox check` found it stopped (it
  refuses a unit whose file in `/etc/systemd/system` outranks the mask);
- with `sandbox.close-resolved = true`, closes systemd-resolved to every
  user but root and the runner's ([below](#network));
- installs `setup.packages` (dnf or apt) and `setup.npm`, as root and on
  the open network; npm versions must be exact;
- installs `setup.agents` from npm tarballs pinned in the binary
  (`src/sandbox/setup/agents.toml`): every package of each agent by its
  SHA-512 integrity, unpacked by `agentic-job` into
  `/opt/agentic-job/agents` with no npm and no install script, its
  programs linked in `/usr/local/bin`; a tarball that does not match its
  pin is refused, and the pins are for Linux on x86-64 with glibc;
- denies the sandbox user sudo, every polkit action, cron, at and
  lingering;
- if configured, runs the caller-pinned `setup.tools` installer as that
  user, without runner credentials, before network lockdown;
- starts the egress proxy and loads the network rules (below);
- refuses a host where the world-write policy is not loaded (secure-host
  loads it first: [secure-host.md](secure-host.md#access-time-world-write-policy));
  with `sandbox.filesystem-view = true`, installs the read-only view on the
  user's manager and every `run0` command; raises `ptrace_scope` from 0 to 1;
- runs `setup.script` as the sandbox user, never as root;
- installs the root-owned helper and configuration under `/etc/agentic-job/`;
- by default, locks the runner's user out of general sudo and polkit,
  closes root-equivalent group access. [The lock and its probes](sandbox-check.md#after-setup-nothing-has-root)
  describe the remaining privileged operations.

The world-write policy applies to every user but an object's owner, the
runner's user included, and `sandbox check` probes it for both users. The view
is opt-in, `sandbox.filesystem-view = true`, on top of it. The view confines
the sandbox user's processes, not the runner's subsequent steps, supervision
or cleanup.
A root-owned drop-in on the **system** unit `user@UID.service`
and properties on each transient `run0` service set `ProtectSystem=strict`
and `ProtectHome=read-only`, with
`ReadWritePaths=` for the user's home, `/run/user/UID`, `/tmp` and `/var/tmp`.
User services inherit the manager's mount namespace: clearing their own path
properties does not undo it. This is not a sandbox setting on a slice or scope.
The kernel API trees `/proc`, `/sys` and `/dev` are exceptions, as defined by
`ProtectSystem=strict`: making `/proc` read-only prevents writing uid/gid maps,
and read-only cgroups prevent the delegated user manager and Podman managing
their units. They remain governed by kernel and ordinary permissions, not
an exception for arbitrary host storage. `/dev/shm` is shared temporary storage.
Device access, including KVM, remains subject to ordinary permissions. The
view does not grant permissions or make a read-only filesystem writable.
No `PrivateUsers`, `PrivateDevices`, mount syscall filter or `NoNewPrivileges`
is added: those would hide KVM or break Podman's subordinate-id helpers.

After package installation, setup stats the paths in
`crates/agentic-job/src/sandbox/setup/privileged-binaries.tsv`, following
links (Ubuntu's `/usr/bin/sudo` is an alternatives link to sudo-rs). A listed
path absent from the image is skipped; one present as a non-regular file or
with a different uid, gid or mode refuses setup. This is a metadata check of
known binaries, not a content check or an inventory, and it does not search
the filesystem. Setup has no filesystem traversal, so this allowlist
is its only setuid check: it neither finds nor strips unknown
image-supplied setuid programs. That accepts what the operator decided for
the view in #188, now for every host, and needs a trusted fresh image without
arbitrary root-shell helpers. Distribution subordinate-id helpers remain
available with and without the view.

The Ubuntu 26.04 entries were stat-checked in a fresh `ubuntu:26.04`
container with the relevant packages installed, not on a GitHub-hosted runner
image; the RHEL entries on a RHEL 10.2 devspace, not a stock host. Neither list
proves stock-image completeness. Setup fails closed on deviations; do not
silently accept them or add unknown paths by scanning the filesystem.

There is one trusted exception: systemd 257 forks `(sd-pam)` before applying
the mount namespace. It runs systemd/PAM code, not agent-supplied code. The
probes require that another process of the sandbox uid cannot attach with
ptrace, write its memory, open its memory file or use its `/proc/PID/root`.
They test both run0 and manager handlers, with positive memory-write and
ptrace controls and the separate host `ptrace_scope` check. `hidepid` hides
these nondumpable handlers from their own uid, so the probe finds them in
the control groups of the manager and of the run0 command. A hosted test
kills a sacrificial run0 handler and verifies that its surviving command
still cannot write outside the view. Killing the handler does not necessarily
end its parent session in systemd 257; it offers no new execution path.

The read-only view is not a kernel boundary and does not block Unix socket
IPC. The existing local-service/socket allowlist probes still apply. Trusted
host code must not propagate new writable host mounts after setup: systemd's
path restrictions do not make such later mounts read-only. The untrusted user
has no privilege to create those mounts in the host namespace.

Hosted setup logs remain the timing source, including the new
`filesystem-view` stage. Local tests cannot supply this pull request's hosted
before/after timings; those must be collected from its CI stage lines.

Every command in the sandbox is then started through the root-owned
helper, which invokes `run0 --pipe --user=…`. This creates a transient
service with its own PAM session
and none of the caller's environment. It gets a fixed `PATH` and `LANG`,
the proxy's variables and `sandbox.env`; a variable named `ACTIONS_*`
(the job's identity-token request is two of them) is refused by name in
the configuration and again at entry. `--pipe` needs systemd 257; setup
refuses a `run0` whose `--version` names an older one.

### Why a systemd read-only view has not replaced the walk

The walk has since been replaced, by the access-time world-write policy
([secure-host.md](secure-host.md#access-time-world-write-policy)), not by the
view. The kernel applies the policy by uid to every process, whatever its mount
namespace, `(sd-pam)` included. What follows is why the view alone did not meet
that condition, and why it stays an opt-in layer.

The proposal in [#188](https://github.com/cgwalters-forge/agentic-job/issues/188#issuecomment-6081914015)
would prevent writes to world-writable host paths outside the sandbox's own
directories without inventorying the image. It must cover every process running
as the sandbox user, not just the command `run` launches. The
proposed two-unit guard does not meet that condition.

In systemd **257**, the [execution documentation](https://github.com/systemd/systemd/blob/v257/man/systemd.exec.xml)
distinguishes these cases:

- `ProtectSystem=strict` makes the hierarchy read-only **except** `/dev`,
  `/proc` and `/sys`. `ReadOnlyPaths=/` instead selects the root explicitly.
  `ReadWritePaths=` can carve out the home, runtime and temporary directories;
  it preserves ordinary permissions, not grants access, and cannot override a
  read-only filesystem superblock. `PrivateTmp=yes` with `ProtectSystem=strict`
  leaves the unit's private `/tmp` and `/var/tmp` writable.
- A root-installed drop-in on `user@UID.service` configures a **system**
  service, even though its executable is `systemd --user`. Its children inherit
  its mount namespace. This is different from asking that user manager to apply
  filesystem settings to individual user units, which the user controls.
  For those user units, the documented
  [availability rule](https://github.com/systemd/systemd/blob/v257/man/system-or-user-ns.xml)
  for `ReadOnlyPaths=`/`ReadWritePaths=` implicitly enables `PrivateUsers=`
  and requires unprivileged user namespaces. The sandboxing overview says most
  filesystem namespacing settings need `PrivateUsers=true` in a user manager.
- [run0's `--property=`](https://github.com/systemd/systemd/blob/v257/man/run0.xml)
  sets properties on its newly created transient **service**. `--user=NAME`
  selects the Unix identity, not the per-user manager. The properties are not
  a policy on every process with that uid, nor execution settings on a slice
  or a session scope.

There is a specific process outside both proposed views: **`(sd-pam)`**.
`run0` always uses the `systemd-run0` PAM stack; the upstream
[user manager unit](https://github.com/systemd/systemd/blob/v257/units/user@.service.in)
also has `PAMName=systemd-user`. The execution documentation describes the
long-lived PAM session handler. In the v257
[executor](https://github.com/systemd/systemd/blob/v257/src/core/exec-invoke.c),
`exec_invoke()` calls `setup_pam()` before `apply_mount_namespace()`.
`setup_pam()` forks `(sd-pam)`, drops it to the target uid/gid with
`fully_set_uid_gid()`, and leaves it waiting to close the session. Only the
parent continues to install the unit's mount restrictions and exec the command.
Thus both PAM handlers retain the system executor's filesystem view, not the
restricted view of the command or user manager. Adding the same properties to
both units does not change that order. This is source evidence of an uncovered
process, **not** a demonstrated way for agent code to take over the PAM handler
or access its `/proc/PID/root`; no such exploit was tested here.

Compatibility is also not proved merely by accepting the properties.
`PrivateUsers=true` maps only root and the unit identity (units launched by a
non-root per-user manager omit root); `identity` maps only the first 65,536 ids.
Neither provides the subordinate-id mappings needed by this project's rootless
Podman setup.
`NoNewPrivileges=yes` prevents setuid/file-capability elevation by `newuidmap`
and `newgidmap`; denying `@mount` prevents container mount operations. Those
are not suitable blanket fixes while retaining rootless Podman. Keeping host
`/dev` avoids hiding `/dev/kvm`, whereas `PrivateDevices=yes` would hide it.
Read-only path settings do not block Unix socket IPC, and writable mounts
propagated later from the host remain writable inside the unit; the manual
explicitly warns of both limitations. Namespace support may also be gracefully
disabled, so a successful unit start is not proof of enforcement.

For the all-process requirement, the view stopped at the PAM-handler exception
rather than replace the walk behind a partial guard. The world-write policy
that did replace it is a boundary of that kind: the kernel checks it at access
time, whichever process attempts the write, so it holds before PAM forks.

## Network

The nftables rules match the sandbox user's uid and its subordinate
uids, so containers are covered, and reject rather than drop. The cloud
metadata address is always rejected. With `egress.proxy` (the default),
everything else is rejected too except loopback, and loopback's port 53
with it: the proxy resolves names. `egress.direct` lists endpoints
reached without the proxy, each an IPv4 address and port on the tailnet;
it is for the [inference proxy](inference.md), so that the run token
never crosses the egress proxy. With any, the rest of the tailnet is
rejected by name as well. The proxy's own uid is rejected on the tailnet
and on private, loopback and link-local addresses, except for TCP and UDP
port 53 at literal resolvers read from `/etc/resolv.conf` during setup.
New connections to other DNS destinations, including public ones, are rejected.

systemd-resolved, where it runs (the hosted Ubuntu image, not the RHEL 10
runners), resolves names for any local user over its Varlink socket and
the system bus, and asks upstream as itself, so the rules above do not
stop the sandbox user sending data out in names. With
`sandbox.close-resolved = true` setup takes other users' access off the
sockets in `/run/systemd/resolve/` (the runner's user loses them too)
and installs a bus policy that refuses calls to `org.freedesktop.resolve1`
by default and allows root and the runner's user. Both refuse by who connects, not by uid range, so the
subordinate uids of a container are refused too. It does so wherever
resolved is running (even if masked) or can start, since a call on
the bus or a connection to a socket would start it; drop-ins in
`/etc/systemd/system` keep the socket units' modes when they are made
again. This requires systemd 258 or newer where resolved uses socket
activation; setup refuses older versions, whose daemon-created sockets
cannot be closed before publication by a post-start chmod. Glibc's lookups through
nsswitch's `dns` use the stub on loopback and need neither. Off by
default; the hosted configurations turn it on.
The existing established/related-connection exception is unchanged. Tailnet
denials precede these exceptions. For a [session run](../specs/session.md),
the sandbox user is also rejected on loopback at the session bridge's port and
at the node's own tailnet addresses, before any of its accepts. Otherwise the
agent could reach the bridge itself and claim the operator's login. The loaded
text stays in `/etc/agentic-job/rules.nft`.

The design follows a suggestion cgwalters made for the gh-aw fork
([comment](https://github.com/cgwalters-forge/gh-aw/issues/1#issuecomment-5958830932)).

## The egress proxy

The policy needs the method and path of every request, so the proxy has
to end TLS. One that did not could only allow by host name, and would
lose the rule that reads are open and writes are not.

By default the binary runs its own proxy (`sandbox egress-proxy`,
`crates/agentic-job/src/sandbox/proxy/`), on hyper and rustls, with the
policy of `egress/` ported from `policy.py`, the same refusals and the
same access log as mitmproxy, and setup needs no Python or package
index. It speaks HTTP/1.1 to both sides, where mitmproxy also speaks
HTTP/2: a client offered only HTTP/1.1 uses it. With `[egress]
rust-proxy = false` in the host configuration
[mitmproxy](https://mitmproxy.org), pinned in `egress/requirements.txt`,
runs the addon and policy of `egress/` instead, which the binary
carries; setup installs it into a Python environment, so the host needs
`python3-venv` in `[setup] packages`. That switch stays until mitmproxy
is removed ([#919](https://github.com/cgwalters-forge/agentic-job/issues/919)):
CI's baseline sandbox shard runs the probes against mitmproxy, the
others against the Rust proxy.

Either starts on `127.0.0.1:3128` as the user `egress-proxy`, in a
transient unit with no capabilities and a read-only system. The key of
its certificate authority stays in that user's state directory; the
certificate is published in `/etc/egress-proxy`, and the sandbox user's
environment points `HTTPS_PROXY` and the bundle variables of `git`,
`cargo`, `curl`, Node and Python at both. The Rust proxy checks the
servers it connects to against Mozilla's roots, as mitmproxy does with
certifi's.

A `GET`, `HEAD` or `OPTIONS` without a body may go to any host that is
not on a threat feed. Anything else, a WebSocket and a read with a body
included, needs a `[[write]]` rule: the ones shipped allow `git fetch`
from six forges, `gh`'s GraphQL reads and `npm audit`, and
`egress.policy` replaces them. Downloading packages, such as Cargo's
from crates.io, is reading and needs no rule
([toolchains](dispatch.md#giving-runs-a-toolchain)). The proxy does not
read a GraphQL query, so a mutation passes it too: only GitHub's
enforcement of the agent's read-only token stops a write there. A push is refused. So is a
request whose `Host` header or TLS name is not the host it connected
to, and with raw TCP off, anything in a tunnel
that is not HTTP. Under `inference.front`, the Rust proxy also refuses
the sandbox user the broker, before any policy and by name or address
([fronting](inference.md#fronting-the-broker)). A refusal is a 403 with the reason in
`X-Egress-Denied`. The log is one JSON line per request with method,
host, path and decision, never headers, bodies or query strings; `run`
copies the part written during the run into the transcript.

### Opt-in domain allowlist

An attacker can leak data in a GET URL to their own server even without a
request body. Write rules alone do not stop that threat. To restrict destinations,
add this table to the proxy policy file selected by `egress.policy` in the host
configuration (or the action's `egress-policy` input):

```toml
[egress]
mode = "allowlist"
allow = ["example.com", "packages.example.org"]
```

This is the **proxy policy file**, not the host configuration's `[egress]`
table. Keep the `[[write]]` rules needed by the caller in that same file;
selecting a file replaces, rather than extends, the shipped policy. Select it
from trusted caller configuration, never dispatcher-controlled workflow inputs
or agent-produced files.

The gate applies to CONNECT and every HTTP request, including destinations of
redirects and writes. A write still needs its write rule; the threat feed and
Host/TLS-name checks still apply. Entries match the named domain and all its
subdomains on label boundaries, ignoring case and one trailing dot; an entry
with more than one trailing dot is refused rather than normalized. Use ASCII
DNS names (punycode for international names), not URLs, ports, wildcards or IP
literals. IP-literal destinations are refused in this mode. At most 256 entries
of at most 253 characters are accepted; an empty list denies every destination.

An entry without a dot names one of [gh-aw](https://github.github.com/gh-aw/)'s
ecosystem identifiers, such as `github`, `containers`, `node` or `python`,
and stands for its group of hosts, from gh-aw's
`pkg/workflow/data/ecosystem_domains.json` at the commit CI pins gh-aw to.
[`ecosystem_domains.json`](../egress/ecosystem_domains.json) records that
commit and the file's hash; CI regenerates it with
[`ecosystems.py`](../egress/ecosystems.py) and fails on any difference.
An unknown identifier is refused, as are gh-aw's compound identifiers, which
are not in that file. Each host of a group is then checked like an entry
written out, and counts against the 256: gh-aw's `*.x` becomes `x`, which
already covers the subdomains and adds only `x` itself, of the same owner;
any other wildcard, loopback name or IP literal in a group (`local` has
them) refuses the policy. Nothing is allowed that the policy does not name.
Groups include shared hosting domains, such as `githubusercontent.com` in
`github`, with the risk described below.

Omitting the table, or setting `mode = "reads-anywhere"` without `allow`, keeps
the reads-anywhere default. A [private run](private-repositories.md) requires
`mode = "allowlist"`, but the mode alone does not admit one: allowed domains can still
receive data in URLs, and allowing a shared hosting domain or
attacker-controlled subdomain delegates that risk to its owner. Network address
restrictions remain unchanged; this adds no access to private addresses.

## What is tested

`sandbox check` probes all of this as the sandbox user, each probe with
a positive control. `run` does not repeat it: before the agent starts
it runs only its own probes that the run token is nowhere but the
agent's configuration. CI's `sandbox` job runs setup and the check for
real on hosted `ubuntu-26.04`, then removes each
protection in turn and requires that the matching probes fail
(`tests/sandbox_host.rs`), after showing that setup refuses a machine
that is not fresh (`tests/sandbox_fresh.rs`). What that runner cannot
show, and what was tried by hand elsewhere, is
[listed with the probes](sandbox-check.md#where-each-probe-has-been-seen-to-fail).

## What it does not do

- The runner's user still owns the checkout, caches and job credentials,
  and has unrestricted network access. Removing its root does not make
  it safe to run untrusted code as that user. `sandbox.lock-runner = false`
  also keeps its general sudo access.
- Reads are open, so data can leave in a `GET` to a host that is not on
  the feed. The feed is fetched once, at setup; a fetch that fails, or
  returns fewer than 1000 entries, leaves the proxy without one, with a
  warning.
- With `egress.proxy = false` the sandbox user's network is open but for
  the metadata address, and the tailnet when `direct` has entries.
- A container the agent starts has no network of its own. It reaches the
  proxy only on the host's network, and trusts it only if the
  certificate is mounted into it, as the probes do; nothing configures
  podman to do either. Use the [container recipe](secure-host.md#containers)
  for networked builds and runs.
- The agent can read whatever is world-readable on the host, and connect
  to whatever listens for every local user unless the caller stops it.
- `setup.npm` runs the packages' install scripts as root, which is why
  the list is the caller's and never the task's. `setup.agents` runs
  none, and installs only what a release of this repository reviewed.
- Setup needs Python's `venv`, a package index, `curl` and `nft` on the
  machine. It has run on `ubuntu-26.04` in CI; other images are the
  caller's to try.
