# Threat model

## Attacker and trust

The attacker controls an unprivileged later CI step: a build script, dependency
hook or pull request's code. The kernel, boot image, root setup, hardening
binary, BPF object and configuration are trusted. Setup must finish before
untrusted code starts. Root compromise, a malicious runner image and kernel
exploits are outside this model. Use a fresh disposable host for each job.

## Boundaries

The runner lock removes routes from the job user to root, including sudo,
privileged executables and container sockets. The fixed privileged helper
is not a general root command runner. World-write BPF enforcement stops
the job user changing files it does not own merely because they are writable
on the root filesystem's device. Other mounted filesystems are outside that
device-scoped policy and need their own permissions or isolation.
Owner-writable controls must remain writable or the probe fails.

The runner-read policy, when enabled, limits reads of other runner processes'
environment and memory. Setup also closes diagnostic sockets and discards
core dumps so a step cannot recover an ancestor's credentials from a dump.
These controls do not make same-UID processes mutually isolated: files,
inherited environment, permitted IPC and job tokens remain shared trust.

Network rules refuse metadata/private-network routes according to the
configuration. Optional egress write policy constrains HTTP methods and
destinations through the TLS-intercepting proxy. Its CA and private key are
root/proxy-owned; untrusted code must not be able to replace policy or trust
configuration. Allowed destinations, direct exceptions and the runner's
artifact channel are still potential exfiltration channels. An allowlist is
not a guarantee that a destination cannot store attacker-controlled data.

## Non-goals and evidence

No confidentiality boundary separates later steps of the same job. Do not
give a job a credential or private input it must hide from its own code.
Use separate jobs/hosts and read-only tokens; validate untrusted outputs
before a privileged publisher consumes them. Resource exhaustion, malicious
build results and supply-chain verification of fetched dependencies remain
the caller's responsibility.

`secure-host check` probes the configured boundary, not every possible
kernel or network attack. Success without a required control's negative
and writable positive controls is not proof. Unit tests and ordinary CI
are unprivileged; privileged runtime evidence must come from disposable
supported runners. A skipped probe is not a passed security claim.
