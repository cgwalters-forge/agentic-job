## The gap

The [external-fetch contract](../docs/dispatch.md#binary-correlation-interface)
stops an unrelated run, a second attempt or a substituted hand-back from
becoming publication authority. It knows the caller and the producer only
through GitHub Actions:

- `Record::caller_env` and `caller_policy` compare the record with
  `GITHUB_REPOSITORY`, `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT`
  ([external.rs](../crates/agentic-job/src/external.rs#L57-L67),
  [L262-L268](../crates/agentic-job/src/external.rs#L262-L268)). Policy
  ([policy.rs](../crates/agentic-job/src/policy.rs#L840-L842)) and check
  ([check/mod.rs](../crates/agentic-job/src/check/mod.rs#L661)) call them,
  as does `external-release`, so on GitLab all three refuse.
- `identity` reads a workflow run's `path`, `head_sha`, `triggering_actor`,
  `run_attempt` and `referenced_workflows`
  ([external.rs](../crates/agentic-job/src/external.rs#L369-L426)).
- `artifacts` reads the jobs of attempt 1 and named artifacts carrying an
  API `digest` ([external.rs](../crates/agentic-job/src/external.rs#L472-L531)).
- The release check requires the branch `agent-run-RUN_ID`
  ([external.rs](../crates/agentic-job/src/external.rs#L95-L105)).

The [GitLab guide](../docs/gitlab.md) supports a same-pipeline,
deterministic producer whose artifacts reach check through `needs:`. That
path stays unchanged. This document adds the cross-pipeline case: a trusted
GitLab pipeline starts a producer pipeline, possibly in another project,
and publishes only what it re-checks itself.

## Roles

- The **caller pipeline** runs only trusted configuration from its
  project's protected default branch, on fresh runners tagged
  `agentic-job-trusted`, as the guide's jobs do
  ([prerequisites](../docs/gitlab.md#prerequisites-and-unsupported-cases)).
  Its dispatch, fetch, check, detect and apply jobs are separate jobs.
  Pipeline-variable overrides must be limited to trusted operators, as the
  [guide's pipeline](../docs/gitlab.md#minimal-deterministic-pipeline)
  requires. Pipeline variables override YAML variables, so whoever can set
  them chooses the binary that runs beside the publisher token.
- The **producer pipeline** runs the producer on a producer runner, or later
  on a Testing Farm guest ([below](#testing-farm-as-a-later-layer)). It holds
  no publisher, read-API or provisioning credential that the producer can
  reach. Until the agent can run on GitLab at all ([out of scope](#out-of-scope)),
  only a deterministic producer can use this path.
- The **guest** is the machine the agent's code runs on. Nothing it writes
  is authority. Only bytes fetched by job ID and re-checked are used.

## The caller-owned record

A dispatch job in the caller pipeline creates the producer pipeline with
`POST /projects/:id/pipeline` and immediately writes the record. The record
is uploaded only as that job's artifact, for later caller jobs, and never
goes to the producer. GitLab's create call returns the pipeline's `id`, so
the record always names it. GitHub's `dispatch_id`, run-name matching and
ten-minute appearance window ([external.rs](../crates/agentic-job/src/external.rs#L428-L470))
have no counterpart. They exist only because a `workflow_dispatch` might not
return its run.

The record has exactly these fields, with the same strict JSON, 64 KiB
limit and `deny_unknown_fields` as `Record`
([external.rs](../crates/agentic-job/src/external.rs#L110-L144)):

- `forge`: exactly `gitlab`; `server`: the instance's HTTPS URL, equal to
  the caller's `CI_SERVER_URL`. Caller and producer use the same instance.
- `caller_project`, positive `caller_project_id`, `caller_pipeline_id`
  and `caller_job_id`: the caller pipeline and the job that wrote the record.
- `profile_commit`, `kind` (exactly `implement`), `target_repository`,
  `target_branch`, `base_commit` and positive `item`: unchanged from the
  GitHub record. `target_repository` is a GitLab path, nested groups
  included.
- `project`, positive `project_id`: the producer project. This can be the
  caller's own project.
- `reference` and `commit`: the producer pipeline's branch and full SHA.
- `ci_config_path`: the producer project's CI configuration path as
  reviewed. An empty string means GitLab's default `.gitlab-ci.yml`, which
  the API may report as `null` or `""`.
- `pipeline_id`: the ID the create call returned.
- `user_id`: the numeric GitLab user of the dispatch credential.
- `variables`: the exact pipeline variables passed at creation, as
  `{key: value}`. Among them, `AGENTIC_JOB_RELEASE` and
  `AGENTIC_JOB_SHA256` name the producer's agentic-job binary.
- `agentic_job`: the full commit the release tag resolved to when its
  attestation was verified
  ([pinned release binaries](../docs/gitlab.md#pinned-release-binaries)).
  GitLab has no counterpart to `referenced_workflows`, so nothing checks
  this field against the run. It is the caller's evidence, named in the
  draft.
- `agent_job`, `check_job` and `detect_job`: distinct, exact job names in
  the producer's configuration at `commit`.
- `dispatched_at` and `deadline`: RFC3339. The lifetime is at most 330
  minutes, as `MAX_LIFETIME_SECONDS` already bounds
  ([external.rs](../crates/agentic-job/src/external.rs#L22)). It must also
  fit the fetch job's own `timeout`.

### Re-deriving the record from the API

The fetch job holds only a read token for the producer project. It takes
nothing from the producer's artifacts or logs except the agent job's
archive. Before downloading, it checks the record's caller and producer
fields against GitLab. The target fields (`profile_commit`, `target_*`,
`base_commit`, `item`) are the caller's own, which policy and
`external-release` apply as on GitHub.

1. **Caller.** `CI_SERVER_URL`, `CI_PROJECT_ID` and `CI_PIPELINE_ID` equal
   the record's. This replaces the `GITHUB_*` comparison. GitLab has no
   pipeline attempt: retrying a job keeps the pipeline ID, and a new
   pipeline gets a new one. So later caller jobs in the same pipeline may
   reuse the record, as apply-only retries do on GitHub, and another
   pipeline cannot. The caller pipeline's job list, `include_retried`, must
   hold `caller_job_id` as the only job of its name. Threat: a retried
   dispatch job creates a second producer pipeline with a fresh record, and
   GitLab apply has no re-run guard to stop a second draft. GitHub's
   `caller_attempt` stops the same thing.
2. **Project.** `GET /projects/:id` returns `project_id` with
   `path_with_namespace` equal to `project`, and `ci_config_path` equal to
   the record's. Threat: a Maintainer points the project's CI configuration
   at a file in another project or on a moving ref, so `commit` no longer
   pins the jobs that ran. This reads the setting at fetch time, and GitLab
   does not report which configuration a pipeline was created from. The
   jobs are pinned by `commit` only when the reviewed configuration
   includes nothing but local files and full-SHA project refs. The producer
   project's Maintainers are trusted not to change the setting between
   dispatch and fetch, and to keep project, group and instance CI/CD
   variables in order. Neither shows in this API.
3. **Pipeline.** `GET /projects/:id/pipelines/:pipeline_id` has
   `project_id`, `sha` equal to `commit`, `ref` equal to `reference`,
   `source` `api`, `user.id` equal to `user_id`, and `created_at` no
   earlier than 2 minutes before `dispatched_at`. That is the same
   clock-skew margin `identity` allows
   ([external.rs](../crates/agentic-job/src/external.rs#L394-L403)). Its
   `yaml_errors` are empty, and it is `success` before the deadline.
4. **Variables.** `GET /projects/:id/pipelines/:pipeline_id/variables`
   equals `variables` exactly: the same keys, values and `env_var` type, and
   nothing more. GitLab sets these only at creation, so the check confirms
   that the pipeline is the one the dispatch job described. Threat: the
   dispatch step, or a GitLab feature that adds pipeline variables, ran the
   pipeline with a binary pin or task other than the reviewed one. The
   reviewed configuration at `commit` downloads `AGENTIC_JOB_RELEASE` and
   checks it against `AGENTIC_JOB_SHA256`, as the guide does. `spec:inputs`
   are not in this list, so the producer configuration must take none.
5. **Jobs and attempts.** List
   `GET /projects/:id/pipelines/:pipeline_id/jobs?include_retried=true`,
   with the existing page bounds
   ([external.rs](../crates/agentic-job/src/external.rs#L354-L367)). There
   must be exactly one job named `agent_job`, one named `check_job` and one
   named `detect_job`. Each must be `success`, with `pipeline.id`,
   `pipeline.sha` and `pipeline.ref` equal to the record's, `user.id` equal
   to `user_id`, and `erased_at` null. GitLab has no attempt number. A
   retried job is a second job of the same name, so "exactly one, including
   retried" is the GitLab form of `run_attempt == 1`. The per-job user
   check stops a manual job that another user played, possibly with job
   variables the pipeline list does not show.

The fetch repeats steps 2–5 after the download, as `fetch` re-lists before
release ([external.rs](../crates/agentic-job/src/external.rs#L600-L616)).
Any HTTP failure, pagination overflow or mismatch refuses, and no receipt is
written.

## Artifact identity

GitLab has no artifact ID and publishes no artifact digest. A job's archive
is addressed by its job ID (`GET /projects/:id/jobs/:job_id/artifacts`).
The job listing gives only `artifacts_file.filename` and `size`. So:

- The raw hand-back is the archive of the one `agent_job` job, by its ID.
  The `check_job` and `detect_job` successes are early filters only, as on
  GitHub ([correlation](../docs/dispatch.md#correlating-a-dispatch-with-its-external-run),
  step 6). Their archives are never downloaded.
- The fetch downloads the archive under the existing bounds: at most
  128 MiB, the central-directory and flat-file checks, no restored modes
  ([external.rs](../crates/agentic-job/src/external.rs#L747-L866)). Its
  length must equal the listed `size`. It hashes the bytes itself, and
  never sends the read token to a redirect target
  ([external.rs](../crates/agentic-job/src/external.rs#L685-L704)).
- The receipt holds the record, `agent_job_id`, `check_job_id`,
  `detect_job_id` and `raw` as `{size, digest}`, where `digest` is
  `sha256:HEX` of the downloaded bytes.

The digest does not prove provenance. On GitHub, the digest comes from the
same API that serves the bytes, so it protects only the transfer
([dispatch.md](../docs/dispatch.md#correlating-a-dispatch-with-its-external-run),
step 5). On GitLab, the fetcher computes it, so it only records what the
fetcher received. It lets later caller jobs and the draft name exactly those
bytes. In both cases the archive was uploaded by the runner that ran the
agent job, so the agent could have written any content there. Provenance
rests on the job being the only one with its name in a pipeline whose
project, configuration, commit, user and variables the record fixed. Even
then, the content is untrusted data that the caller's own check reads.

## Where re-check and apply run

Only caller jobs, on caller runners, under the caller's bounds:

1. **Fetch** writes the receipt and the extracted raw files as its own
   artifact. Like `external-fetch` today, it writes no policy or command.
2. **Policy** runs `policy --external-receipt` with the caller's bounds.
   The receipt narrows only as it does on GitHub: `implement` only, the
   exact target and base, no push or secondary target, and drafts only
   ([policy.rs](../crates/agentic-job/src/policy.rs#L840-L863),
   [external.rs](../crates/agentic-job/src/external.rs#L270-L280)).
3. **Check** collects and checks the fetched files with the ordinary
   patch, protected-path and size checks.
4. **Detect** runs the caller's own threat detection.
5. **Apply** runs `external-release` before any write
   ([external.rs](../crates/agentic-job/src/external.rs#L69-L108)). That
   gate holds the checked patch to `base_commit` and its branch to
   `agent-run-PIPELINE_ID`, the producer pipeline's ID. How the producer's
   `run` names that branch from `CI_PIPELINE_ID` is left to the
   implementation. Then it runs
   `apply --forge gitlab`. A draft merge request is a `Draft:` title
   ([publishing to GitLab](../docs/safe-outputs.md#publishing-to-gitlab)).
   The publisher token is scoped to apply's environment
   ([secrets](../docs/gitlab.md#publisher-secrets-and-lifecycle)).

None of these jobs runs on the producer runner or a guest, and none runs
producer code. The producer's configuration may compose its own policy and
check. The caller never reads that output.

## Testing Farm as a later layer

This layer can follow only after the agent can run on a guest at all,
which is [out of scope](#out-of-scope). Then the producer's `agent_job`
launches the guest and runs no agent code itself:

- **Provisioning.** The launcher holds a Testing Farm API token. Its job
  environment scope keeps that token off other jobs. The launcher submits
  one request with the plan's repository and a full-SHA ref, a compose, and
  `settings.pipeline.timeout` within the job's minutes. The token never
  enters the request's environment or secrets, so it never reaches the
  guest, where a wrapper command line has exposed secrets before
  ([inference.md](../docs/inference.md#on-a-multi-user-guest)). Machine
  reservation is refused. Threat: a reserved guest keeps the agent's
  workspace reachable over SSH after the job.
- **Cancellation and destruction.** When the job is cancelled or times out,
  the launcher's `after_script` sends `DELETE /v0.1/requests/ID`. The
  request's pipeline timeout is the backstop. Testing Farm's request page
  does not document guest destruction, so it is an unverified prerequisite,
  as the job host's teardown is in
  [resources, lifetime and cleanup](../docs/dispatch.md#resources-lifetime-and-cleanup).
- **Result transport.** The launcher downloads only its request's
  hand-back from Testing Farm's artifact storage, under the archive bounds
  above, and uploads it as its job archive. It parses only the archive
  structure those bounds need, and never runs the content. A failed,
  cancelled or oversized result uploads nothing.

The layer changes only where the agent ran. The record, the
[re-derivation](#re-deriving-the-record-from-the-api) and the caller's jobs
stay the same. The Testing Farm request ID that the launcher reports is
evidence for the draft, not authority. Binding it would require the fetcher
to read the request from Testing Farm's API against a pinned plan ref. That
is a separate decision.

## Mapping from the GitHub contract

| GitHub (`external.rs`, `dispatch.md`) | GitLab |
| --- | --- |
| `repository`, `repository_id`, `reference`, `commit` | `project`, `project_id`, `reference`, `commit`: one-to-one |
| `triggering_actor_id` on the run | `user_id` on the pipeline **and on each job**, since another user can play a manual job |
| `check_job`, `detect_job` succeed | same, by job name; `agent_job` added because artifacts belong to jobs |
| page, archive, ZIP, timeout and redirect bounds | one-to-one |
| `--external-receipt` narrowing, `external-release` gate | one-to-one |
| lifetime at most 330 minutes | one-to-one; must also fit the fetch job's `timeout` |
| `GITHUB_REPOSITORY`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT` | `CI_SERVER_URL`, `CI_PROJECT_ID`, `CI_PIPELINE_ID`; **new:** the dispatch job `caller_job_id` not retried |
| `dispatch_id`, run-name match, `returned_run_id` optional | dropped: `pipeline_id` is always returned and recorded |
| `run_attempt == 1` | **new:** exactly one job per name with `include_retried` |
| `workflow` path and `referenced_workflows` pins | **new:** `ci_config_path` equal to the record's; `commit` pins the jobs only with local or full-SHA includes |
| profile `inputs` fixed by the map | **new:** exact pipeline `variables`, which carry the binary pin |
| artifact by name with API ID and digest | **new:** archive by job ID; fetcher-computed digest checked against API `size` |
| `agent-run-RUN_ID` | `agent-run-PIPELINE_ID` |
| `agentic-job-applied` names keyed to the caller run | **gap:** GitLab apply has no re-run guard. A retry may post again ([no deduplication markers](../docs/safe-outputs.md#neutral-inline-comments), [run summary](../docs/safe-outputs.md#publishing-to-gitlab)); for `implement`, the existing branch refuses a second push |

One mechanism carries this: `external-fetch --forge gitlab` takes the
record above, and the receipt carries `forge` so policy and release check
the caller with the matching variables. The GitLab path is opt-in, used
only when a caller passes `--forge gitlab`, and the GitHub path stays
unchanged. Detection on GitLab is not
shipped. How the caller's detect job reports its result to
`external-release` is open, and apply refuses without that result.

## Out of scope

- **Inference credentials for guests.** `run --runner-home` refuses
  `inference.register = "api-key"` because the agent could read the key
  ([run/mod.rs](../crates/agentic-job/src/run/mod.rs#L535-L538),
  [inference.md](../docs/inference.md#a-provider-api-key)). GitLab has no
  supported broker registration
  ([gitlab.md](../docs/gitlab.md#prerequisites-and-unsupported-cases)).
  Changing that is the operator's threat-model decision, and nothing here
  depends on it or changes it.
- `fix`, secondary targets, a different output repository, and a producer
  on another GitLab instance.
- Record creation, the dispatch credential and its role, and Testing Farm
  admission. These belong to the caller, as on GitHub.

## Acceptance

Each refusal needs an offline API fixture, as
[tests/external.rs](../crates/agentic-job/tests/external.rs) has for
GitHub, and its positive control: one recorded pipeline whose jobs match
is released. Refuse a caller variable mismatch, a retried dispatch job,
another pipeline, a wrong
project ID or path, a changed `ci_config_path`, a wrong `sha`, `ref`,
`source` or user, a pipeline variable added, removed or changed, a retried,
erased, missing or failed `agent_job`, `check_job` or `detect_job`, an
expired archive, a size or digest mismatch, a result after the deadline, and a hand-back on another
base or branch. A live proof against the disposable GitLab used by CI's
`gitlab` job follows the offline fixtures.
