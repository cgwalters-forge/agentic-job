# Session runs: an agent the operator talks to

A session run is an ordinary `agentic-job run`, with the same policy, sandbox,
inference proxy, limits, hand-back, check and apply. It does not end after the
task's turn. After that turn it waits for a client's prompts, and each prompt is
a turn of its own. The task is the session's profile, for example the
controller's instructions with agent-board read-only. The run ends when the
client leaves, when no prompt arrives within the idle timeout, or at a limit.
The transcript is the run's artifact, as for any run. A new session starts from
the forge, not from an old transcript.

It is off by default. Only a configuration with `[session] listen = true`, from
the reusable workflow's `session` input, turns it on. The caller's file names
`operators`, `origins` and an optional `capability` once; without `listen` they
are inert.

**Breaking change to unreleased behaviour**: the first version of this slice
dialled out to a relay. `[session] relay` and `audience`, and the workflows'
`relay` and `relay-audience` inputs, are gone; a configuration or call that
still names them is refused.

## Agents and ACP

The session already drives every agent over ACP on its standard streams
([harness](../docs/harness.md)):

| Agent | ACP | How |
| --- | --- | --- |
| opencode | native | `opencode acp` |
| Vibe | native | its `vibe.acp` library entry point, with project configuration off ([agents.toml](../crates/agentic-job/src/session/agents.toml)) |
| Claude Code | adapter | [`@agentclientprotocol/claude-agent-acp`](https://github.com/agentclientprotocol/claude-agent-acp), pinned in [policy.yml](../.github/workflows/policy.yml) |
| Codex | adapter | [`@agentclientprotocol/codex-acp`](https://github.com/agentclientprotocol/codex-acp); not in this registry |

Claude's adapter ends a running turn when a prompt arrives during it. The bridge
avoids this by refusing a client's prompt while a turn runs. The client cancels
the turn or waits for it. This holds for the task's turn too: a client that
cancels it has the session go on to its prompts.

## Shape

```text
review board (browser, ACP client pane), on the operator's tailnet device
   │ wss://RUNNER.TAILNET.ts.net/: TLS from serve, the operator's identity
tailscale serve on the runner, which adds Tailscale-User-Login or
   │ Tailscale-App-Capabilities
   │ http://127.0.0.1:7790, loopback
bridge, inside `run`, as the runner's user
   │ stdio
agent, also as the runner's user (before #2989, a sandbox user entered
   through run0)
```

The runner is on the tailnet, which takes incoming connections, so the bridge
listens and the operator's client connects to it. The bridge is part of `run`,
the process that already holds the agent's ACP connection
([bridge.rs](../crates/agentic-job/src/session/bridge.rs)). It listens on
loopback port 7790 only. `sandbox setup`, which has root, writes the address
`wss://NAME/` for the runner's tailnet name to `/etc/agentic-job/session-endpoint`;
before a secure-host image of this source, `[host.prepared] serve-port` has
the image's setup write it.
Setup prints it in the job's log. The run action puts it in the job's
summary and its `session-endpoint` output, and `agentic-job.yml` passes that on
as a job and workflow output. Summaries and outputs resolve only when the job
ends. While the session is live, a caller's wrapper names the endpoint from the
hostname its own join step gave the runner (such as `agentic-job-RUN_ID-ATTEMPT`)
and the tailnet's DNS name, and posts it to the dispatch issue, where the pane
finds the session. The tailnet needs HTTPS certificates enabled, and the runner
must have joined it before secure-host, as for the inference proxy. Setup
refuses a runner whose name is not among `tailscale status`'s `CertDomains`:
serve would otherwise wait for the HTTPS capability until it timed out. A
configuration with `listen` and no `agent.name` is refused. Once `run` binds
the port, its root helper holds a duplicate listener and enables
`tailscale serve --bg --https=443 http://127.0.0.1:7790`. A private control socket
ties that helper to the supervisor's lifetime. On normal cleanup or supervisor
exit, including a crash, it disables that HTTPS mapping before releasing the
listener. With `[session] capability` set, the helper adds
`--accept-app-caps=CAPABILITY`, read from root's copy of the configuration,
never from its caller. A mapping that "does not exist" is already off. If disabling fails,
root retains the port, even when ending the agent's processes failed,
and retries ten times before only holding it until the host ends the job.

Each runner's name gets its own certificate. That puts the name and the
tailnet's in public Certificate Transparency logs, and many sessions in a week
can run into the certificate authority's rate limits. The helper, which gives
`tailscale serve` 30 seconds, or the operator's first connection would then
fail. Neither has been tried on a real runner.

The chat pane belongs to [cgwalters-forge/review](https://github.com/cgwalters-forge/review)
([review#66](https://github.com/cgwalters-forge/review/issues/66)). The page's
`connect-src` needs `wss://*.TAILNET.ts.net`.

## Wire

A client opens a WebSocket at the endpoint. Each text message, either way, is
one of ACP's JSON-RPC messages; a binary message is answered as not JSON. The
bridge plays the agent toward the client and serves only these methods:

| Client sends | Bridge does |
| --- | --- |
| `initialize` | answers itself, with no capabilities |
| `session/new` | attaches the client to the running session and returns its id; `cwd` and `mcpServers` are ignored |
| `session/prompt` | sends a turn to the agent, and refuses the prompt if a turn is already running |
| `session/cancel` | passes the cancel on to the agent's turn |
| anything else | error `-32601` |

Before attaching, the client receives no notifications. After attaching, it
receives every one of the agent's notifications, with the run's secrets
replaced in each string, as in the job log. The task's turn may still run when
the client attaches. Its prompts are refused until that turn ends, so it
cancels the turn or waits for it.

The handshake is refused with HTTP 403 unless it is let in by a login or by a
capability. By a login, both of these hold:

- `Tailscale-User-Login` is there once and is one of `[session] operators`.
  `tailscale serve` sets it to the login of the user whose device connects, and
  drops one the client sent. A tagged device gets none.
- `Origin` is there once and is one of `[session] origins`, compared as a
  browser sends it (`https://review.example.ts.net`).

A tagged device, such as the operator's agent host, is let in by a capability
instead, where `[session] capability` names one, such as
`example.com/cap/agentic-job-session`. Serve then forwards
`Tailscale-App-Capabilities`, a JSON object of the node's accepted capabilities
that the tailnet policy's grants give it, and drops one the client sent. Both
of these hold:

- `Tailscale-App-Capabilities` is there once, printable ASCII of at most
  4 KiB, and a JSON object with the capability as a key. Anything else is
  refused with its own reason. Tailscale encodes a value that is not ASCII
  as RFC 2047, which is not decoded, so it is refused as not JSON.
- `Origin` is absent, as from a client that is no browser, or there once and
  one of `[session] origins`. A browser on that device always sends one, so
  a page of another site cannot use the device's capability.

A login with no `Origin` is still refused: only the capability takes a client
without one. `operators`, `origins` and `capability` come from the caller's
configuration file, which the calling repository owns, never from a workflow
input a dispatcher sets. `operators` may be empty when `capability` is set.
Who holds the capability is the tailnet policy's to decide, in a grant such as:

```json
{"src": ["tag:agent-host"], "dst": ["tag:ci-runner"],
 "app": {"example.com/cap/agentic-job-session": [{}]}}
```

Its source must not include the tag CI runners join with. Otherwise another
job's steps on another runner could attach to the session. A refused handshake
leaves the bridge listening.

`agentic-job session connect ENDPOINT` is a client for a terminal or another
agent. It sends `initialize` and `session/new`, then each line of standard
input as a `session/prompt`, waiting for that turn's answer before the next.
It sends a prompt again while the task's turn runs. It prints the agent's
`agent_message_chunk` text with control characters replaced, so the agent
cannot drive the operator's terminal. With `--json` it prints each message
from the bridge as one line of JSON instead. It checks serve's certificate
against Mozilla's roots, and takes `ws://` only to loopback. At the end of its
input it leaves, which ends the session. The first client let in is the
only one: later connections are closed unanswered, and when that client leaves
the session ends.

## Trust boundaries

**The operator's client** can send prompts to this one session and cancel its
turns. It can see what the agent says. That makes it as trusted as the task's
author, and the caller's configuration names it as the caller chooses the task.
It cannot:

- change the policy, output types, egress, limits or the agent's tools, all of
  which are fixed before the agent starts;
- start a program, because `mcpServers` is dropped;
- open another session;
- answer permission requests, which the run's policy answers whether or not
  someone is watching;
- get a credential: the session holds none for it.

**Who can attach** is decided by the bridge from what serve adds. Each check
stops one thing:

- The login check keeps out every other tailnet device and user the tailnet's
  access rules let reach the runner.
- The capability check does the same for tagged devices, which have no login:
  only a node the tailnet policy grants `[session] capability` gets in. The
  grant, not the repository, then decides which nodes may attach. A grant
  whose source includes the CI runners' tag would let any job's steps on a
  runner attach. The network rules once kept the sandbox user from its own
  runner's grant; none holds the runner's user, so the grant's source
  excluding the runners' tag is the only thing that keeps the agent from
  using it.
- The `Origin` check keeps out a page of another site open in the operator's
  browser. That page's connection would otherwise carry the operator's tailnet
  identity (cross-site WebSocket hijacking). It holds on the capability path
  too whenever there is an `Origin`, which a browser always sends.
- Nothing keeps the agent out. The network rules kept the sandbox user from
  port 7790 on loopback and from the node's own tailnet addresses, which
  `sandbox check` probed ([the session's bridge](../docs/sandbox-check.md#a-sessions-bridge)).
  They never held the runner's user, which is now the agent, and they are
  gone. The agent can connect to the bridge with a forged
  `Tailscale-User-Login`, or through serve as the node's owner, take the
  one client slot and prompt its own session. [Option
  (a)](#a-lift-the-refusal-the-job-is-the-unit-of-trust) says what that
  does and does not give it.
- `run` binds the port before the agent starts. Its root helper retains the
  port until serve is revoked, even after a failed reap or supervisor exit.
  This kept a sandbox user from binding the free port and being handed later
  connections through serve, with the operator's login on them. It still
  keeps the runner's user, the agent included, from the port until serve
  is revoked when `run` ends or is killed. After that it does not: ending
  the run kills the agent's process group, not a process it moved to a
  session of its own (`setsid`), and such a process can bind the free port.
  It cannot have serve forward to it again: the helper's `session-serve`
  records its first use in a root-only directory under `/run` and refuses
  every later call, and the host is thrown away after its one job. So a
  surviving process gets only the free port, which the tailnet no longer
  reaches.
  While `run` runs, setup's ptrace restriction (Yama scope 1 or
  more, [secure-host.md](../docs/secure-host.md)) keeps the agent from
  attaching to its parent `run` and taking the listener. The agent does not
  need the port: it can connect to it as a client. Setup
  does not enable serve: a probe or setup process holding the port makes `run`
  fail without exposing that process to the operator.
- `Origin`s are `https://`, or `http://` for localhost only. Script injected
  into a plain-HTTP page elsewhere would connect with the operator's identity.

Loopback is reachable by the runner's other processes: the job's own steps,
as trusted as `run`, and since #2989 the agent too. Encryption to the operator's device comes from
serve's TLS over the tailnet (WireGuard).

**What the agent can cause** is no more than in a task run. Its words reach the
client with the run's own secrets replaced. Other secrets it has read are not
replaced, as in the transcript. Its hand-back is still checked on another
machine and applied only by `apply` ([safe outputs](../docs/safe-outputs.md)),
during the session too once [writes during a session](#writes-during-a-session-specified-not-built)
are built.

## Limits

A session run stays inside the run's timeout and budget. Hand-back near a limit
also works the same, whether a turn is running or the session is idle. The idle
timeout is `session.idle-minutes`: 10 by default, at most 60. It runs from the
end of the task's turn whether or not a client has come. A runner waiting
for nobody still costs minutes. Hosted jobs end after six hours. At most 16
operators and 16 origins are taken, and one capability.
`Tailscale-App-Capabilities` is taken up to 4 KiB. Up to 16 handshakes run concurrently, each
with a 10-second deadline. At capacity a new connection replaces the oldest
pending handshake, so parked sockets cannot reserve every slot. This does not
prevent sustained connection flooding. Messages from the client are capped at
512 KiB, twice the largest task. A longer message ends the connection. At most four client requests wait for the session at once. At most
8 MiB of lines wait to be sent to the client. A response waits for room, so the
bridge stops reading a client that does not read. An agent's notification that
finds no room ends the connection, and the agent goes on. `session connect`
takes messages of up to 8 MiB, the most the bridge queues, and refuses an
input line or prompt over the bridge's 512 KiB.

## Running a session without a second user

A second user gave the session two things. The agent could not reach the
bridge, so only a client serve vouched for could attach. And it could not act
as `run`: neither take its listener or connection nor upload to the run with
its credential. Under [the runner-only model](../docs/sandbox.md) the agent is
the runner's user, and neither holds. Three ways back follow.

### (a) Lift the refusal: the job is the unit of trust

`run` and the reusable workflow accept `listen` again, and the spec accepts
that the agent can attach to its own session. The job holds
nothing the agent may not have, so this gives it:

- the first, and only, place on the bridge. It can attach before the operator
  with forged serve headers and prompt itself, and the operator's connection is
  then closed unanswered. That denies the operator the session, which the
  agent could already do by exiting, killing `run` or answering nonsense;
- an operator confirmation it can forge, so nothing that arrives over the
  bridge can gate a write.

The operator's prompts reach the agent anyway, and what reaches the client is
still what `run` passes on: the agent's notifications, redacted. The agent
cannot attach to `run` to write to the operator's connection itself (see the
port's retention above). A client still treats every message as the agent's:
`session connect` prints only `agent_message_chunk` text, with control
characters replaced, and answers no request from the bridge.

It does not give the agent a credential: the bridge holds none, the operator's
client sends none, and `run` still refuses the job's OIDC request credential
and what else only a second user kept from the agent. It gives no write: the
hand-back is still checked on another machine and applied only by `apply`. It
gives no reach to other runners' sessions: that is the tailnet policy's,
through the login check and a capability grant whose source leaves out the
runners' tag. And it gives no more time or budget than the run's limits.

### (b) Keep the bridge out of the agent's reach

The root helper, which already holds the port and enables serve, would run the
bridge itself, on a Unix socket in a directory only root can enter, and point
serve at it: `tailscale serve --bg --https=443 unix:/run/agentic-job/session/bridge.sock`.
Serve takes a `unix:` target for HTTP from Tailscale 1.94 on (not in 1.92.0):
the CLI's help gives `tailscale serve unix:/var/run/myservice.sock`
([serve_v2.go at v1.104.2](https://github.com/tailscale/tailscale/blob/v1.104.2/cmd/tailscale/cli/serve_v2.go)),
and the reverse proxy adds `Tailscale-User-Login` and
`Tailscale-App-Capabilities` for such a target as for a TCP one
([ipnlocal/serve.go](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go)).
[The serve documentation](https://tailscale.com/kb/1242/tailscale-serve)
names only `http://127.0.0.1` targets and does not mention sockets. The
tailnet-join action's pinned `tailscale/github-action` v4.3.0 installs 1.104.2
by default. tailscaled runs as root and can dial the socket; the runner's user
cannot.

That stops the agent from attaching with forged headers, and the operator
keeps the session. The agent can still reach serve through the node's own
tailnet address, since the network rules hold no one; serve then sends the
runner's tagged identity, which gets in only if the capability grant's source
includes the runners' tag, as in (a). It
does not stop the agent from playing everything on the far side of the
bridge: `run`, the ACP stream and whatever channel connects `run` to the
helper are the runner's user's, so the helper must take all of it as the
agent's. It also does not make writes during a session trustworthy. The
operator's confirmation would stay in root, but Actions gives root no upload
credential the check job could tell from the agent's (see
[writes during a session](#writes-during-a-session-specified-not-built)). The
cost is a WebSocket and header parser running as root and reachable from the
tailnet, where today it runs as the runner's user, and a relay protocol
between the helper and `run`.

### (c) An nft match the agent cannot escape

`run` would start the agent in a cgroup owned by root, and the rules would
refuse sockets of that cgroup (nftables' `socket cgroupv2`) at the bridge's
port and the node's tailnet addresses. The agent cannot move itself out of a
cgroup whose parent it cannot write. But it is the runner's user, and other
processes of that user live outside the cgroup. It can have the user's
systemd manager start a process for it (`systemd-run --user`), and rootless
podman, which the work this was built for needs, puts containers in the
user's slice. It can also act as `run` itself. A socket's cgroup is the one
its creator was in, so any of these escapes the match. Closing them takes the
user manager, and podman with it, away from the agent: a second user in all
but name.

### Recommendation: lift the refusal

(a) is recommended. It is the model docs/sandbox.md already states: the job is
the unit of trust, and the agent may hold whatever the job does. (b) would buy
the operator's place on the bridge at the price of root parsing tailnet
traffic, and it would not bring back writes during a session. (c) is not a
boundary.

**Security consequences.** "Only the operator can attach" becomes "only the
operator, or the agent itself". The login, capability and `Origin` checks
still keep out every other tailnet device and user, and other sites' pages.
A session the agent has taken is a denied session: the operator sees their
connection closed and ends the run as they would a stuck one. Nothing that
arrives over the bridge may authorise anything, so writes during a session
wait for the end-of-run apply. [Job/token separation](../docs/workflow.md)
and the [safe-output contract](../docs/safe-outputs.md) do not change. The
agent job keeps read access and holds no write token. The agent still never
gets the OIDC request credential, beside which `run` refuses to start. Check
and apply run on other machines, and only `apply` holds `SAFE_OUTPUTS_PAT`.

### Runtime code it needs

Built:

- `run` no longer has `session` in `refuse_without_second_user`; its other
  refusals stay, and `a_session_run_talks_to_its_operator_and_hands_back` in
  [run.rs](../crates/agentic-job/tests/run.rs) starts `run` with `listen`.
- [runner-setup.py](../workflow/runner-setup.py) admits `session.listen`;
  its test admits it on and off and still refuses it beside a private
  caller or target, `api-key` or `[mcp]`.
- `network.rs` no longer writes the bridge's rules for the empty
  `sandbox_uids` set.
- The documentation says `session.listen` is taken and what it gives the
  agent.

The root helper's port retention, serve's revocation, the header checks and
the endpoint stay as they are. Writes during a session need a replacement for
their premise first. No second user comes back for any of it.

## Writes during a session: specified, not built

Today the agent writes requests to `safe-outputs.jsonl`, and those requests are
checked and applied after the run. A conversation needs some applied while it
runs: comment, dispatch a planned job, set a board field.

The prior art is gh-aw's [safe-outputs MCP server](https://github.com/github/gh-aw/blob/0cff1a907e29222854708e8174944697e1fe34f9/actions/setup/js/safe_outputs_mcp_server.cjs).
It runs outside the agent's container with the read-only job token and appends
each validated tool call to a JSONL file. The writes still happen in a separate
safe-outputs job after the agent's job
([compiler](https://github.com/github/gh-aw/blob/0cff1a907e29222854708e8174944697e1fe34f9/pkg/workflow/compiler_safe_outputs_job.go)).
gh-aw does not apply outputs during a run either.

The agent job keeps no write token, because
[job/token separation](../docs/workflow.md) is the boundary, and no job or host
holds a standing write credential for the session either: the operator's own
GitHub session starts each write. A write during a session is the end-of-run
check and apply, run early on part of the hand-back:

1. `run` reads the outputs file append-only: a line once read is never read
   again, so a later change to it is not seen. It checks each new request
   against the run's policy with `check`'s code, and sends a request that
   passes, with its index N, to the client as one ACP notification, as data.
   After the first request that fails, it sends no more: every later upload
   would hold it, and check would refuse it.
2. The chat pane shows the request as text. When the operator confirms it, the
   pane sends that back over the bridge, as an ACP extension method. Only then
   does `run` upload everything it has read, up to and including request N, as
   the artifact `session-outputs-ATTEMPT-N`, and answer with the upload's ID and
   digest. A request the operator does not confirm is never uploaded.
3. The pane dispatches tracker's session apply workflow with the operator's own
   GitHub session. The inputs are the session's run ID, N, and the upload's ID
   and digest. They only select; none is trusted.
4. That workflow's check job, read-only like [check.yml](../.github/workflows/check.yml),
   looks the run up. It refuses one that is not a `workflow_dispatch` run of
   tracker's own session workflow on tracker's default branch, or not its
   first attempt. It looks the upload up in that run, and refuses it unless it
   is `session-outputs-1-N` with the digest given; the download fails on other
   bytes, as for the hand-back today. It takes the run's `agentic-job-policy`
   artifact and holds it to tracker's bounds file again. Then it checks the
   whole upload with `check`'s code, ceilings included, and passes request N
   on alone, with its index, as `checked-outputs`.
5. Its apply job applies that with `SAFE_OUTPUTS_PAT`, as
   [apply](../docs/workflow.md#running-apply-again) does today: same pinned
   handlers, same guard, and the same hidden name
   `agentic-job-applied: RUNID/POSITION/DIGEST`, with the session's run ID,
   artifact prefix and N, not its own.
6. At the run's end, `run` hands back what it read. The end-of-run check checks
   all of it, so each request applied during the session counts against the
   ceilings again, and apply's guard leaves out each one already posted.

**The request was trustworthy to the apply job** because it came from the
run, not from the dispatch. **That no longer holds since #2989.** The argument
was that only `run`, as the runner's user, could upload to the run: the
sandbox user never got `ACTIONS_RUNTIME_TOKEN`
([process.rs](../crates/agentic-job/src/session/process.rs) drops it), and the
caller's own steps are as trusted as `run`. Now the agent is the runner's
user. Whatever credential would let `run` upload, `run` would hold as that
user, where the agent can read it (as `run`'s refusal of a private target
already says of the runner's Actions-service writes). So it could
upload `session-outputs-1-N` itself, with any content, before `run` does, and
confirm its own requests over the bridge. The checks below would then pass
uploads the operator never saw, and the ceiling argument fails: an upload is
no longer always a prefix of what `run` read. `agent-user: sandbox`, which this
design required of tracker's session workflow, is refused. Under the
[recommended option](#recommendation-lift-the-refusal) nothing in the job is
out of the agent's reach to upload, so **writes during a session wait for the
end-of-run apply**. What would replace the premise is an upload, or a record of
the operator's confirmation, made by a principal the runner's user cannot act
as and that the check job can tell apart: another job, or a service off the
runner. Actions gives the root helper no credential of its own to upload
with, since `ACTIONS_RUNTIME_TOKEN` is the runner's. The rest of this section
records the design for that day. Each check stopped one thing:

- Refusing a run of another workflow, event or branch stops the uploads of a
  fork's pull request run in tracker, of any other job there, or of a session
  workflow changed on a branch, from being applied with `SAFE_OUTPUTS_PAT`.
- Requiring the name and digest given stops a later upload under another ID
  from replacing the one the operator saw: what is applied is what the pane
  showed. The digest is the server's; the input only has to match it.
- Checking again on a separate machine keeps `run`'s check from being a
  boundary: it only keeps the pane from offering what would be refused.
- Checking the whole upload, not request N alone, keeps the ceilings: every
  upload is a prefix of what `run` hands back at the end, so whatever is
  applied lies within a prefix that passed. If the agent could upload, it
  could post single requests that each pass and together exceed them.
- Taking only the first attempt keeps the prefixes those of one record. A
  re-run of the whole session run is a new agent run under the same run ID,
  and its end-of-run apply counts its own requests only, as a re-run of all
  jobs does today.

Uploading on confirmation makes the operator's confirmation the gate. Anyone
else who can dispatch tracker's workflows can apply only a request the
operator already confirmed, so the apply job need not check who dispatched it.
A request applied during the session stays applied when the end-of-run check
refuses the hand-back, for a later invalid request or the ceiling. A request
the operator did not confirm is applied at the end if that check accepts it,
as today.

**The ledger of applied requests** is the hidden names apply already writes:
the forge itself, as for a re-run of apply. No new marker or store is needed
if a request has one name whichever job applies it: the run, the index and
the digest of the prefix and the request. The append-only read fixes the
request and its index, if `check` keeps or drops each item by its own content.
Today apply computes the digest after it puts a partial run's note in a body
and folds a review's findings into its comment, so a comment applied during
a session that then ends at its timeout would get another name at the end,
and be posted again. The digest must therefore be computed from the request
as check accepted it, before those rewrites; a re-run sees the same checked
request either way. The rest are the guard's limits:

- It counts only posts by the token's principal, so both applies must post as
  the same one: a `SAFE_OUTPUTS_PAT` that `GET /user` names, the same in both,
  or the job token in both.
- It finds an issue through the forge's search, which lags seconds behind,
  and the end-of-run apply can follow a confirmation that closely. So
  `create_issue` waits for the end. Comments, including those of
  `close_issue`, are listed directly.
- Labels, closing and project fields carry no name and are done again, which
  leaves the forge as once unless someone undid them in between, as an
  operator in a conversation might.

A request with a patch, `create_pull_request` or `push_to_pull_request_branch`,
waits for the end too: its patch is the run's end product.

The guard looks before it posts, so two applies of one run at once could both
post. Every apply of a session run, in the session or at its end, needs one
concurrency group named by the session's run ID. Today the reusable workflow
sets none, and a caller's group covers the whole run, which would hold every
in-session apply until the session ended. So the apply job sets its own,
named by the run ID it applies for. Actions cancels a pending job when
another joins the group, so a late dispatch can cancel a pending end-of-run
apply. A cancelled apply posts nothing, and someone has to re-run it or
dispatch it again: a write can be late or lost that way, never doubled.

**Security consequences.** The agent job's permissions do not change: read
access, and no OIDC request credential or write token for the agent.
`run` uploads artifacts during the session, with the runtime credential the
runner's user already holds in JavaScript actions. That credential also writes
the Actions cache. The design assumed the way `run` gets it kept it from the
agent; with the agent as the runner's user nothing does, which is why this
design waits. The check and apply jobs keep their separation and their tokens;
neither executes anything the agent produced, and both take the request as
data. What is new is a write credential in the operator's browser: the GitHub
session that dispatches must hold `actions: write` on tracker, and anything
that runs script in the pane's origin can then dispatch any of tracker's
workflows as the operator. The pane renders the agent's requests, so it must
show them as text, never as markup.

[Session.tla](Session.tla) models this beside [Pipeline.tla](Pipeline.tla):
apply runs during the session for any request, at any time, and again at the
end, with re-runs. TLC checks that only checked requests are applied, none
twice, within the ceiling, and that no writer runs the agent's code; each
property has a broken variant TLC rejects ([README](README.md)). The model
assumes that the upload for request N is the prefix of what `run` read, up
to N: that only `run` uploads. Since #2989 that assumption does not hold, so
its results say nothing about a session run today. It is left unchanged until
a replacement for the premise is concrete enough to model.

Left open:

- "Dispatch a planned job" needs a safe-output type like gh-aw's
  [`dispatch_workflow`](https://github.github.com/gh-aw/reference/safe-outputs/),
  which the bounds do not have. It must not be able to name tracker's session
  apply workflow.
- The operator decides whether the pane's GitHub session may hold
  `actions: write` on tracker. No runtime code is written before that.
- What replaces "only `run` uploads": which principal outside the runner's
  user uploads, or records the operator's confirmation, and how the check job
  tells its uploads from the agent's. Until then nothing below is built.
- How the uploader gets `ACTIONS_RUNTIME_TOKEN`, which only JavaScript actions
  see, without adding JavaScript; moot if the uploader is not in the agent's
  job.
- Whether a request the operator declined should be refused at the end.

## The first slice

The slice was built with a sandbox user. From #2989 `run` refused
`[session] listen`; it takes it again with the runner's user as the agent,
which can attach to its own session (see the status above). It has six parts:

- `[session] listen`, `operators`, `origins`, `capability` and `idle-minutes`;
  the reusable workflow's `session` and `idle-minutes` inputs set the first and
  the last;
- the root helper serving the bridge's port with `tailscale serve`, and the
  endpoint published by the run action (the network rules that kept the
  sandbox user from the port are gone with it);
- the bridge;
- the conversation loop in the session driver;
- `session connect`, a terminal's or another agent's client;
- tests in [session.rs](../crates/agentic-job/tests/session.rs). In them a
  scripted WebSocket client on loopback, with the headers serve would add, is
  refused without a login, with another login, with a bad `Origin`, and with a
  missing, other, duplicated or malformed capability. Then the
  operator attaches, is refused what the bridge does not serve, sends a prompt
  and reads the reply, cancels a turn, and goes quiet until the idle timeout.
  `session connect` attaches over `ws://` through a stand-in for serve that
  adds the capability, and drives two turns.
  These tests drive the bridge and the session driver without `run`.
  [run.rs](../crates/agentic-job/tests/run.rs) drives `run` itself with
  `listen`, as the runner's user: a scripted client on loopback attaches
  with the headers serve would add, has a prompt answered with the run's
  secrets replaced, and leaves, and the run hands back what the agent
  wrote in that turn. With `AGENTIC_JOB_TEST_SANDBOX_USER` set, the
  conversation test once ran the agent as a second user entered through
  run0; no host has that user now.
